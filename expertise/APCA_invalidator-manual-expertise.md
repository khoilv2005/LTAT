# Manual domain expertise for APCA Invalidator

This expertise is grounded in the patch-correctness-assessment literature (Invalidator [Le-Cong et al., TSE 2023], Panther [Tian et al.], DiffTGen, ODS) and the characteristics of patches generated by Automated Program Repair (APR) tools (kPAR, jGenProg, AVATAR, Cardumen, RSRepair, Nopol, ARJA, SimFix). It is intended to be combined with data-driven heuristics so the model has both general principles and dataset-specific cues.

## Definitions

- **Correct Fix (CoF, Class 1)**: a patch that is semantically equivalent to the developer-written reference fix. It addresses the actual root cause and does not introduce new failures or unrelated behavior changes.
- **Non-Correct Fix (NCF / Incorrect, Class 0)**: a patch that passes the test cases used by the APR tool but is not semantically equivalent to the reference fix. The patch typically over-fits the test suite, masks the bug, or alters unrelated behavior.

## Strong signals that a patch is INCORRECT (NCF)

Treat any of these as strong evidence of NCF:

1. **Dead code / unreachable guard**: blocks like `if (false) { ... }`, `if (1 == 0) { ... }`, `while (false)`, conditions that can never trigger. These are typical of overfitting (the change adds code only to short-circuit a failing test).
2. **Tautological condition flip**: changing `==` to `!=`, `<` to `<=`, `&&` to `||`, or boolean literals (`return true` / `return false`) without semantic justification, especially when the surrounding logic is non-trivial.
3. **Removing a safety check that was actually needed**: removing a non-null guard, range check, or bounds check, leaving the next line vulnerable to NPE / out-of-bounds.
4. **Hard-coded literal substitution**: replacing a computed expression with a constant that happens to satisfy a test case (e.g., `return result;` becomes `return 42;`, or `dist = compute(...)` becomes `dist = expectedValue;`).
5. **Unrelated change**: the diff touches a method, file, or branch that is not on any plausible execution path leading to the reported bug.
6. **Skip / no-op transform**: wrapping the buggy expression in an empty try/catch, swallowing exceptions, or returning early without computing the intended result.
7. **Wrong abstraction layer**: fixing a symptom in a caller while the root cause is in a callee (or vice versa). Reference fixes usually target the layer where the invariant is broken.
8. **Test-passing trick**: change happens precisely on a value or branch that the failing test exercises, with no general justification (literal matches the test's expected output).
9. **Change inside catch / finally with no propagation**: silencing the bug by hiding the exception path.
10. **Duplicate / contradictory edits**: two edits in the same diff that touch related lines but are inconsistent (e.g., add a check then immediately bypass it).

## Strong signals that a patch is CORRECT (CoF)

Treat any of these as strong evidence of CoF:

1. **Off-by-one fix**: changes `< n` to `<= n - 1`, `i++` placement, or `length - 1` vs `length` exactly where the bug report or context suggests an iteration boundary issue.
2. **Null guard at the right place**: adds `if (x != null) { ... }` or `Objects.requireNonNull(x)` immediately before the first dereference of `x`, where context lines show the value can come from an external source.
3. **Bounds / range check**: adds a check that prevents an index from going negative or exceeding capacity, with the check located before the indexing operation.
4. **Type or cast correction**: replaces a wrong cast or wrong overload with the correct one, especially when the surrounding code shows the original cast loses precision or selects the wrong method.
5. **Operator / comparator correction with semantic justification**: changes `==` to `equals`, `>` to `>=`, etc., when the surrounding context is comparing object references that should be value-equal, or boundary inclusions that should be inclusive.
6. **Resource cleanup**: adds `close()`, releases a lock, or wraps in try-with-resources at the proper site.
7. **State invariant restoration**: re-orders statements, adds a missing initializer, or moves a check so that an invariant documented in surrounding comments holds.
8. **Minimal, focused diff that touches the suspected fault location**: the file path, class name, and method name align with what the bug context suggests, and the change is small and on-topic.

## Heuristics to avoid common mistakes

- **Do not penalize a patch just because it is small.** A correct off-by-one fix can be a single-character change.
- **Do not penalize a patch just because it is verbose.** Refactor-style fixes can be lengthy yet correct, as long as semantics are preserved.
- **Do not penalize a patch just because it is APR-tool generated.** All these dataset patches come from APR tools; both classes contain tool-generated patches.
- **A passing test does not imply correctness.** If the only evidence is "the test passes", and the change looks like a literal substitution or a tautological flip, prefer NCF.
- **Absence of context is not evidence of incorrectness.** If the diff is plausible and minimal, do not assume bug intent only from filenames.

## Decision procedure to follow

1. From the file path, class name, function name, and surrounding context lines (lines without `+`/`-`), state the most likely intended bug in one sentence.
2. List the semantic effect of the patch: which guard, computation, or branch changes, and on which inputs the new behavior differs from the old.
3. Apply the signals above:
   - If any **strong NCF signal** clearly fires: classify as Incorrect.
   - Else if any **strong CoF signal** fires and the patched location matches the inferred bug: classify as Correct.
   - Else: weigh evidence, default to whichever class has more positive signals; do not default by class prior.
4. Output the final answer in the required format.

## On dataset priors

The Invalidator test set is roughly 22% Correct and 78% Incorrect. Use this only as informational context, not as a tie-breaker. Patches arrive in mixed order and each must be assessed on its own evidence.
